How to add up a spending export without trusting it blindly

Short answer

A spending export saved as CSV is easy to add up wrongly: commas inside values, dollar signs, brackets for negatives and blank lines all fool a quick script. This lesson builds a small Python tool that only reads the file, adds up the amounts with Decimal numbers, treats everything as one currency, and lists every row it could not read.

Common mistakes

  1. Splitting on commas yourself. A value such as "Supermarket, weekly shop" has a comma inside quotes. Cutting each line at every comma breaks it. Python has a csv module that follows the quoting rules.
  2. Skipping rows that fail, without saying so. A script that quietly ignores rows it cannot read gives a confident total that is too small. List the rows it skipped, with their line numbers.
  3. Adding money with ordinary decimals. Python's float numbers cannot hold every cent exactly, so tiny errors appear. Python's Decimal type avoids that. This tool accepts only amounts with up to 12 digits before the point and at most 2 after it, and lists anything else instead of rounding it.
  4. Guessing at unclear amounts. Is 12,50 twelve and a half, or twelve thousand and fifty? The tool refuses to guess and lists the row instead.
  5. Trusting a total because it looks neat. Compare with the balance your bank shows. A wrong total looks just as sure of itself as a right one.

Frequently asked questions

How do I add up a bank export in Python?

Read it with Python's csv module, turn each amount into a Decimal, and add the amounts up by category. This lesson builds a small tool that does that and lists every row it could not read.

Will this change my file?

No. The tool only reads the file. A test checks that one small test file has the same bytes and modified time after a run. That is the only evidence for this claim.

Why Decimal and not normal numbers?

Python's Decimal documentation explains that numbers like 1.1 cannot be held exactly as binary floating point, and that Decimal is preferred for accounting where exact equality matters. The tool uses Decimal for amounts with up to 12 digits before the point and at most 2 after it, and refuses the rest.

My file did not work. Why?

The tool expects the columns Date, Description, Amount and Category, dates like 2026-03-15, a dot for decimals, and a comma between values. All amounts are treated as one currency: the tool reads no currency names and converts nothing, so a file that mixes currencies must not be totalled with it. Files with semicolons, a decimal comma or an old text encoding are not supported, and the tool tells you what it could not read.

Can I trust the totals?

Only after you check them. It was tested on a made-up sample and small test files, not on real bank exports. Compare the totals with your bank before relying on them.
